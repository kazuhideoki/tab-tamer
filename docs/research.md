# タブ整理と重複防止の初期調査

この文書は実装前の調査記録。現在の使い方は [README](../README.md)、実装と検証の境界は [implementation.md](implementation.md) を参照。

2026年10月16日。統合拡張は実現可能。通常のBraveプロファイルで、バックグラウンドの重複タブを閉じる際に選択タブが移る現象を再現した。統合するだけでなく、フォーカスの条件と非同期処理の取り消しを設計する必要がある。両拡張の競合が原因かどうかは未確定。

## 確認した環境と設定

- Braveのアプリバンドルのバージョンは155.1.97.57。
- DefaultプロファイルにDuplicate Tabs Closer 4.3.5とAuto-Group Tabs 0.0.24が存在する。Secure Preferencesのdisable_reasonsは両方空。ただし実行中の一時停止状態は未確認。
- リポジトリはREADMEと `.gitignore` のみ。調査前からREADMEに変更、`.gitignore` に未追跡状態がある。
- `/config.toml` は既存の `.gitignore` に記載済み。反映機能は未実装。

保存設定は、対象拡張だけのLevelDBログのwrite batchを順に読み、削除と上書きを適用して確認した。Auto-Group Tabsのgroupsはbase64とLZMAを復号した。ブラウザ稼働中のディスク保存値であり、UI/APIによる現時点の読戻しは別途必要。

| 項目 | 保存値 |
| --- | --- |
| 重複時 | 自動クローズ、残したタブにフォーカス |
| 範囲 | 全ウィンドウ |
| 残すタブ | ピン留め優先、古いタブ優先、HTTPS優先 |
| アクティブ優先 | タブ・ウィンドウとも無効 |
| URL比較 | パス・クエリ・フラグメント・www・大小文字の無視は無効 |
| 例外・追加判定 | ホワイトリストとURLルールは空、タイトル判定なし |
| 空ページ | 除外無効 |
| グループ | 8件。すべてstrict=false、merge=false |

現行のURL比較実装には、上記に加えてHTTPをHTTPSへ置換し、末尾スラッシュを除く処理がある。単純な完全一致と同じではない。個人のグループ名・URLはこの文書に掲載せず、実装時にignoredな設定へ移行する。

## 原因候補と証拠

インストール済みコードの基点は、BraveのDefault/Extensions配下。

- Duplicate Tabs Closer: `gnmdbogfankgjepgglmmfmbnimcmcjle/4.3.5_0`
- Auto-Group Tabs: `danncghahncanipdoajmakdbeaophenb/0.0.24_0`

### 重複防止側単独のフォーカス経路

Duplicate Tabs Closerの `worker.js:224` 付近のcloseDuplicateTabは、タブを削除してからhandleRemainingTabを呼ぶ。同ファイル253〜279行では、activateKeptTabが有効ならdetails.activeに関係なくfocusTabを呼ぶ。`helper.js:126` はタブのactivateとウィンドウのfocusをPromise.allで実行する。

`helper.js:7` のdebounceは初回即時、同じウィンドウ向けの後続要求を500ms間隔で処理する。遅延中のユーザーのタブ切替を取り消し条件にしていない。タブ削除によるブラウザ自身の選択変更も介在する。

インストール済みのdebounceと_handleRemainingTabをNode VMに読み込み、APIをスタブ化して以下を確認した。

1. active=falseの要求でもfocusTabが呼ばれる。
2. 同じウィンドウへ連続要求を入れ、後続の待機中にユーザー切替を模擬しても、タイマー実行時に古い要求先へfocusTabが呼ばれる。

これは制御ロジックの再現であり、Brave上の症状再現ではない。グループ折りたたみとの関係も未確定。DTCはtabGroups権限を持たず、Chromiumのグループを明示的に展開する処理は確認できなかった。

### 自動グループ分けとの競合候補

Auto-Group Tabsの `background.js:5418` 以降はtabs.groupを実行する。merge=trueなら別ウィンドウへ移したアクティブタブを再選択する処理もあるが、保存設定は全件merge=falseなので、この経路を現象の原因と断定できない。

一方、グループ割当と重複クローズは別拡張から独立して走る。移動・削除・取得の間に状態が変わる可能性があり、統合時は共通の処理キューで扱う。現行グループ判定は先に一致したルールを採用し、ピン留め・通常以外のウィンドウを除外する。strict=falseなので、一致しなくなっただけでは既存グループから外さない。

## 統合設計案

Manifest V3のservice workerを中心とする。候補権限はtabs、tabGroups、storage、webNavigation。content scriptや常駐サーバーは基本構成に含めない。

1. イベントをトップレベルで登録し、設定と実タブの初期取得完了後に処理する。
2. タブ生成、URL遷移、選択、ウィンドウfocus、削除・移動を記録する。URL未確定のonCreatedだけで閉じない。
3. まず重複判定を行い、残すタブを決める。決定は全ウィンドウ共通の直列キューで行い、同時に開いたタブがお互いを削除しないようにする。
4. 対象タブのURL・存在・移動先・設定世代を再取得する。前面で開いた意図が現在も有効なら、残すタブのグループ展開、タブ選択、ウィンドウ表示を行い、結果を確認してから新規重複タブを閉じる。
5. バックグラウンド操作ではグループ展開・タブ選択・ウィンドウfocusをしない。途中でユーザーが別タブへ移った場合も古いフォーカス要求を破棄する。
6. 生き残ったタブだけグループ分けする。グループ分け自体は前面表示を要求しない。

API操作は原子的ではない。各await後・副作用直前に世代と実状態を照合し、ユーザー操作と自分の操作に伴うイベントを区別する。判定が曖昧ならタブを残す。フォーカスの完全な無競合をコード構成だけで保証せず、実機でイベント順序を検証する。

`active` は「そのウィンドウ内で選択中」であり、前面ウィンドウとは限らない。外部アプリから開いた際も、単独のactive値から操作意図を断定しない。[Tabs API](https://developer.chrome.com/docs/extensions/reference/api/tabs)、[Windows API](https://developer.chrome.com/docs/extensions/reference/api/windows)

リダイレクト途中のURLでは閉じず、メインフレームの遷移確定を候補にする。SPA遷移・フラグメント変更・読み込みエラーは別に扱う。認証などでは確定後にも遷移するため、待機時間だけで正しさを保証しない。[WebNavigation API](https://developer.chrome.com/docs/extensions/reference/api/webNavigation)

service worker停止後は実タブから索引を再構築する。設定はlocal、ブラウザセッション内の操作履歴は必要に応じsessionへ保存し、古いクローズ・フォーカス処理を復帰時に無条件再実行しない。[Service worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)

### 設定形式と反映

config.tomlはリポジトリ内で編集し、コマンドだけで検証・転送・反映完了の確認まで行う。ユーザー確認済みの方針として、ファイル選択画面や手動リロードを通常の反映手順に含めない。検証済みの設定全体・schema_version・ハッシュ・反映日時をstorage.localへ保存する案とし、失敗時は旧設定を維持する。反映中の処理は設定世代の違いで取り消す。再起動後もlocalから読み込める。[Storage API](https://developer.chrome.com/docs/extensions/reference/api/storage)

CLIから拡張への転送には、コマンド実行中だけ動作するloopback HTTPサーバーと、拡張自身の取込ページを使う案を推奨する。分離したBraveで転送・storage.local保存・完了応答の経路を確認した。詳細は[コマンド反映調査](command-config-research.md)。通常プロファイルでの導入、認証、TOML検証はまだ実装していない。

スキーマ候補は、version、dedup、focus、groups。groupsは安定したid、name、color、順序付きURLルール、非一致時の保持方針を持つ。重複比較とグループ判定は別のルール体系とし、URL正規化は暗黙に追加しない。現在のmatcher構文の意味を移行時に確認する。

config.tomlだけでなく、個人設定を含む生成物・ログ・バックアップもGit管理から除外する。文書の設定例にはexample.com等のみを使う。

## 再現と受入検証

CUAのUI取得はタイムアウトしたが、AppleScriptで通常のBraveプロファイルに接続できた。専用ウィンドウと一時loopbackサーバーのURLを使い、拡張設定を変更せずに測定した。[実測ログ](focus-probe-2026-10-16.jsonl)、[再現スクリプト](../scripts/research/reproduce-focus.py)。

| 実測ケース | 結果 |
| --- | --- |
| 同一ウィンドウの前面オープン | 重複を閉じ、既存タブを選択 |
| 同一ウィンドウのバックグラウンドオープン | 重複は閉じたが、別の選択中タブから既存タブへ切り替わった。要求に反する動作を再現 |
| 別ウィンドウの前面オープン | 既存タブのウィンドウを前面にし、既存タブを選択 |
| macOSのopenコマンドから開く | 既存タブのウィンドウを前面にし、既存タブを選択 |

対象はタブ2136978394、別の選択中タブは2136978396。バックグラウンドケースの前後で選択が8396から8394へ移り、タブ一覧は2件のままだった。元ウィンドウの全タブIDが一致し、終了後のウィンドウ数が1であることを確認した。

測定では一意な仮URLの新規タブを作り、前面ケースのみ選択してから対象URLに変更した。直接URL付きで作る最初の試行は、選択・ID取得前に拡張がタブを閉じる競合があり、前面動作の判定から除外した。今回の結果はCmdクリックや中クリックそのものの試験ではない。通常のWebページでの全操作へ一般化しない。

別途、専用ウィンドウで手動グループを作ったが、UI操作後の折りたたみ状態を確認できず、その試行を有効な再現結果から除外した。テストグループは削除し、テスト用URLのみのウィンドウを閉じた。折りたたみ状態、Auto-Groupの既存ルールに一致するページ、処理中の手動切替、DTC単独との比較は未検証。

検証用ウィンドウと識別可能なテストURLで、下記を「DTC単独」「両拡張」「新拡張のみ」で比較する。既存の普段使いのタブをクローズ対象にしない。

| ケース | 期待する確認 |
| --- | --- |
| 同一ウィンドウ、前面で開く | 既存タブを表示、新規だけ削除 |
| 別ウィンドウ、前面で開く | 既存ウィンドウ・タブを表示 |
| 既存グループが折りたたみ | 前面要求のときだけ展開 |
| Cmdクリック・中クリック | 現在の前面タブを維持 |
| 重複処理中にユーザーが切替 | 切替先を維持 |
| 外部アプリ・アドレスバー・ブックマーク | 各操作の前面表示を確認 |
| 同じURLを連続で開く | 残す対象がぶれず、全削除しない |
| 既存タブ内で別タブと同じURLへ移動 | クローズも既存タブへのフォーカス移動も行わず、戻る履歴を維持 |
| リダイレクト・SPA・hash・query違い | 設定した同一性の範囲のみ閉じる |
| ピン留め・手動グループ・ドラッグ | 既存の保護方針を維持 |
| 最後の1タブが重複 | ウィンドウ消滅とフォーカスの順序を確認 |
| worker停止・ブラウザ再起動 | 設定を維持し、古い操作を再実行しない |
| 不正設定の反映 | 旧設定で動作を継続 |

ログには単調時刻、イベント、tab/window/group ID、選択状態、要求世代、決定理由、API結果を残す。URLは既定で匿名化し、比較結果と操作を追えるようにする。新拡張が通ったことと旧環境の症状を再現したことは分けて記録する。

## 確定事項と残る判断

- 全ウィンドウで重複防止する方針はユーザー確認済み。同一プロファイル内が対象で、別プロファイルとの統合は対象外。
- 重複防止は新しく開いたタブだけを対象とする。既存タブ内のリンク移動・アドレスバー入力・SPA遷移で重複しても、そのタブを閉じたり別タブへ切り替えたりしない。グループ判定は別に行う。
- 設定はコマンドだけで反映する。一時loopbackサーバーと拡張自身の取込ページによる方式を推奨する。認証と通常プロファイルでの操作は実装時に検証する。
- HTTP/HTTPS・末尾スラッシュの同一視、ブラウザ内部ページ、意図的な「タブを複製」、プライベートウィンドウの扱いは実装前に決める。通常／プライベート間は再利用しない案。
- 新規タブの初期遷移と、その後の通常操作の境界を設計する。初期リダイレクト・空タブからの最初の遷移・セッション復元を区別し、タブを一度作ったことを理由に以後の遷移まで削除対象にしない。同一URLでもPOST結果などが同じとは限らないため、初期遷移の判定でも注意する。
- 次の実験は、グループ折りたたみのある既存タブを前面で開く操作と、連続オープン直後の手動切替。旧拡張単独と併用の比較で競合の寄与を判断する。
