# 実装と検証の境界

## 処理

MV3 の service worker がイベントを受け取り、重複処理、グループ分け、設定反映を一つのキューで実行する。新規タブの最初の HTTP(S) 文書だけを候補にし、読み込み完了後の待機時間を経て判定する。空の新規タブも作成からの有効期限内なら最初の Web 遷移を対象にする。既存タブの遷移を候補へ戻す処理はない。

各候補に作成順、文書 ID、URL 変更世代、初期の選択状態を持つ。ユーザーの選択・ウィンドウ移動を追跡し、API 操作の前後に URL、存在、世代を読み直す。前面要求はグループ展開、タブ選択、ウィンドウ表示の順に行い、結果を確認してから新規タブを閉じる。背景要求は表示操作を行わない。生き残ったタブだけをその後グループ分けする。

同じ URL の既存タブが複数ある場合、固定タブ、HTTPS、作成順の優先度で選ぶ。自分より新しいタブを残す相手には選ばない。起動前から存在するタブ間の厳密な作成時刻は取得できないため、同順位はタブ ID で安定させる。

API 呼び出しとユーザー操作を原子的に扱うことはできない。状態変化を検知した場合はタブを保持する。再読み込み、フォーム送信、履歴復元、起動直後、長時間の読み込み、固定・音声再生中・分割表示中の新規タブは閉じない。worker が停止した場合、未完了候補は復元せず保持する。このため重複が必ずゼロになる保証はしない。

Chrome の `active` はウィンドウ内の選択状態であり、OS の前面状態とは異なる。フォーカス移動には両方を確認する。[Tabs API](https://developer.chrome.com/docs/extensions/reference/api/tabs)、[Windows API](https://developer.chrome.com/docs/extensions/reference/api/windows)

## 設定反映

Python CLI が TOML を読み、拡張と共通の JavaScript スキーマで検証する。反映中だけ loopback サーバーを起動し、Brave の起動コマンドで拡張自身の `apply.html` を開く。設定は HMAC、期限、要求 ID、設定ハッシュを検証してから `storage.local` に一括保存し、読戻し後に署名付き ACK を返す。CLI は一致を確認して終了する。設定反映で既存の重複タブを一括削除することはない。

同じ要求 ID・ハッシュは再送可能だが、保存済みより古い反映要求は拒否する。反映失敗や ACK 消失を成功扱いしない。`status` は別の署名付き要求で現在の保存値を取得する。認証情報はローカルの ignored ファイルにだけ置く。通常 Web ページからの外部メッセージ受信は許可しない。

グループの名前・色は固定ルール ID を使って更新する。更新前の設定と名前・色が一致するグループだけを対象にし、手動で編集されたグループは保護する。設定の永続化とグループの再整理は別であり、タブが途中で閉じた等の整理エラーでは保存を巻き戻さない。

## 検証の読み方

`npm test` は URL 判定、署名、非同期処理中の URL 変更・対象消失・ユーザー切替・設定世代変更などの単体テスト。`npm run test:browser` は既存拡張の入っていない専用プロファイルのヘッドレス Brave を使う。API の状態、グループ、選択、設定保存を確認し、結果は ignored な `.test-artifacts/brave-*/results.json`、失敗時は `failure.json` に残す。

既定のヘッドレス試験では AppleScript と macOS `open` を呼ばない。ブラウザ内部のウィンドウ選択・グループ・重複処理を検証する。設定反映の CLI は署名付き要求・ACK を通常通り検証し、テスト専用の `--browser` ランチャーで URL だけを CDP 経由で開く。ヘッドレスの既存プロセスに別プロセスから URL を配送できなかった問題を、この試験用経路で回避する。

`npm run test:browser:headed` は従来の可視試験で、実ブラウザ起動コマンドと macOS `open` のケースも含める。OS の前面状態と製品の URL 配送経路の検証にはこの実行が必要。別アプリへ切り替えると前面再利用の試験は失敗し得るため、通常利用と時間を分ける。既定の試験から可視試験へ自動で切り替えることはない。実行モードと除外ケースは `run.json` に記録する。

通常プロファイルで旧拡張を無効化しての切替、実サイトの認証リダイレクト、ブックマーク、Cmd/中クリック、OS のリンク配送、復元・スリープ後の操作は、専用プロファイルの API 試験から自動的に合格とはしない。導入後の実利用で確認する。

外部コマンドで開いた URL が `start_page` として通知されることを実機で確認した。この遷移種別だけでは復元と区別できないため、一律には除外しない。新規候補、起動直後の保護、読み込み期限、選択の変化を組み合わせて判定する。`start_page` は history API の `auto_toplevel` に相当する。[WebNavigation の遷移種別](https://developer.chrome.com/docs/extensions/reference/api/webNavigation#type-TransitionType)

実際のキーボード操作、Command+クリック、macOS open、AppleScript のタブ操作で、同一／別ウィンドウの再利用、背景での選択維持、リダイレクト待機中の切替、既存タブの遷移を確認した。一時 loopback ルールによる自動グループ分けを画面で確認し、折りたたんだグループが背景では維持され、前面では展開されることも確認した。

検証後は個人設定の元のハッシュへ戻し、テスト用ウィンドウと管理用タブを閉じた。開始時に存在したタブの ID が保持されていることを確認した。通常ブラウザは再起動していない。再起動後の動作確認は前節の専用プロファイルでの結果。各実サイト、ブックマーク、中クリック、スリープ復帰などの日常操作は引き続き確認対象とする。

導入操作では CUA がタイムアウトしたため通常の画面操作を使用した。Apple Events の JavaScript 実行許可を一時変更する案は自動承認レビューで拒否され、その設定は変更せずに導入・検証を完了した。

## グループ内の新規重複に関する追加調査

グループ内の既存タブで重複が残るという報告を受け、次のケースを追加した。

- 初期表示で `history.replaceState` を使い、URLを変えずに状態だけ更新するページ。従来はすべての履歴更新で候補を取り消していた。同じ文書ID・完全に同じURLの場合のみ候補を維持する。ルート・クエリ・フラグメントの変更は従来通り対象外で、既存タブを新たに候補へ登録することもない。
- グループ内の休止タブ。選択後の復帰読み込みで一時的に `pendingUrl` が立つと、既存タブに切り替わった後も新規タブが残った。休止タブを選択した場合のみ、同一URLの復帰がコミットされるまで最大2秒（新規候補の有効期限内）待ち、URL・選択・設定世代を再検証して閉じる。待機中にユーザーが切り替えた場合、別URLに向かった場合、期限を超えた場合は保持する。

これらは再現できた不具合であり、報告された実サイトの原因すべてを特定したという意味ではない。通常のグループ検索自体にはグループ内を除外する条件はなかった。

追加修正後は単体28件、専用プロファイルの回帰18件を確認した。別途、公開GitHubリポジトリを展開済みグループに置いた新規重複の再利用も専用プロファイルで成功した。通常プロファイルでは拡張を再読み込みし、同一URLの履歴初期化を行うページで前面・背景・別ウィンドウ・外部起動・処理中の切替・既存タブ遷移の6ケースが成功した。通常プロファイルの追加AXグループ名取得は失敗し、このUI照合は未検証。個人設定を復元し、元のタブ保持と旧2拡張の無効状態を確認した。[追加検証結果](grouped-duplicates-2026-10-16.json)。
